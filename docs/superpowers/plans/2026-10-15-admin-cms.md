## 1. Contract between the landing page and the CMS

The landing page (Faishal) and the CMS (Farhan) meet at **typed public query functions**. This is the boundary to agree on first.

```
src/features/<entity>/
├── schema.ts            Drizzle tables (CMS)
├── input.ts             Zod-free parsers/validators shared by admin forms (CMS)
├── service.server.ts    Admin mutations with capability guards (CMS)
├── query.server.ts      Admin queries (CMS)
├── public.server.ts     Public read functions: locale-explicit, published-only, safe projection (CMS owns, landing consumes)
└── types.ts             DTOs used by both sides
```

Rules:
1. Public functions take an explicit `locale` and return **published** data only, never drafts, never internal fields (lead data, author emails, storage keys).
2. Every public function has a typed DTO and a fixture used by landing-page component tests, so both sides can work in parallel.
3. Sections hide when their data is empty (PRD rule). The DTO makes "empty" explicit (`[]` or `null`), never placeholder text.
4. Cache tags per entity and locale (`services:en`, `page:home:en`, `settings`) are defined in one file `src/lib/cache/tags.ts` and used by both sides. CPR-33 owns invalidation.
5. Field length limits in the CMS validators match the layout limits in [copywriting.md](../../design/copywriting.md) (headline lengths, meta lengths), so editors cannot break the design.

### 2.5 Media (SeaweedFS)

- Upload to SeaweedFS through a `MediaStore` interface (S3 API, path-style, custom endpoint). Buckets: `media-public` (published assets served via CDN host), `media-private` (draft-only uploads, signed URLs for preview).
- Allowed types: JPEG, PNG, WebP, AVIF, SVG (sanitised server-side, or rejected if sanitising is not implemented), MP4/WebM (≤ 20 MB), PDF (≤ 10 MB). Max image 10 MB, max dimension 6000 px.
- On upload: content-type sniffing (not the extension), random object key with content hash, EXIF stripped, width/height and dominant color stored (for blur placeholders).
- Delivery: `next/image` with a custom loader or remote pattern for the CDN host; responsive sizes generated by Next's image optimiser (no pre-generated variants in v1).
- Library UI: grid, search, filter by type, usage count ("used in 3 places"), delete blocked while in use, replace file keeps the same media ID.
- Alt text required per enabled locale before the media can be used on a published document (FR-ADM rule "alt required").

### 2.6 Email settings (SMTP)

The product owner asked for SMTP configuration in the CMS. The PRD keeps Resend as the provider; Resend also offers SMTP, so both modes are supported.

| Field | Storage | Who |
|---|---|---|
| Mode: `resend-api` or `smtp` | DB | Admin |
| SMTP host, port, security (STARTTLS / TLS), username | DB | Admin |
| SMTP password / Resend API key | **Encrypted at rest** (AES-256-GCM, key from env `SETTINGS_ENCRYPTION_KEY`), write-only in the UI (never displayed, "replace secret" action) | Admin |
| From name, from email, reply-to | DB | Admin |
| Lead notification recipients | DB (Site settings) | Admin |
| Email templates: lead notification (internal), auto-reply (per locale). No waitlist email in v1 (success is shown on screen only); a waitlist template can be added when the product launches | DB, subject + body with placeholders (`{name}`, `{service}`) and a fixed branded layout in code | Admin |
| Test send | Button sends a test email to the current admin, shows the provider response | Admin |

Precedence: if `SMTP_*` or `RESEND_API_KEY` env vars are set, they override DB values and the UI shows "Managed by environment" (production can keep secrets out of the DB entirely). Every change writes an audit entry (§2.7). Email sending stays asynchronous to the form response: lead data is saved first (FR-LEAD-09).

Gotchas: SMTP from a VPS IP is often blocked or lands in spam; prefer Resend API in production and keep SMTP as the fallback. SPF/DKIM/DMARC for the sending domain are required either way (CPR-12).

## 4. Data model changes (migrations)

New tables (Drizzle, reviewed SQL, one migration per ticket):
- `site_settings` (singleton row) + `site_settings_translation`
- `page_content` (`page_key`, `locale`, `data jsonb` validated by a per-page schema in code, `updated_by`, `updated_at`)
- `email_settings` (singleton, encrypted secret columns) + `email_template` (`key`, `locale`, `subject`, `body`)
- `product_capability` + `_translation`, `business_type` + `_translation`, `faq_item` + `_translation` + `faq_item_tag`
- `redirect` (`from_path` unique, `to_path`, `status`)
- `audit_log`
- `media` (+ `media_translation` for alt/caption), `service`, `portfolio`, `post`, `category`, `team_member` per their tickets (CPR-23, 27, 28, 30, 31) with `_translation` tables keyed by `(entity_id, locale)` (PRD §9.4)

### 4.1 Migrations and seed data (every CMS ticket)

Every ticket that adds or changes tables ships **in the same PR**:
1. **Drizzle schema + generated SQL migration** (`npm run db:generate -- --name <ticket>_<change>`), reviewed by hand (indexes, FKs, unique constraints per locale, `ON DELETE` rules). No `db push`, no migration at app start (existing rule).
2. **Seed data** in `scripts/seed/` (one module per entity, run by `npm run db:seed`):
   - `base` seed: structural data the app needs in every environment (site settings singleton with empty optional fields, page keys for every page in [page-patterns.md](../../design/page-patterns.md), email template keys, the 3 service slugs). Idempotent upserts keyed by stable IDs/keys.
   - `demo` seed: **dummy EN content** for development, preview and E2E (hero texts, capabilities, FAQ items, 3 services, 3 work items marked `Internal demo project`, 6 posts, categories, team members, sample leads and waitlist rows, media placeholders uploaded to the local SeaweedFS container). Every demo row carries `is_demo = true` (or a `demo:` key prefix) so it can be listed and removed with `npm run db:seed -- --purge-demo`.
   - Demo copy follows [copywriting.md](../../design/copywriting.md) (no em dash) but is clearly placeholder (`[Demo]` prefix in titles of work items and posts, `example.com` emails, `+62 800 0000 0000` style phone numbers), so it can never be mistaken for real claims.
3. **Guards:** the seeder refuses to run `demo` against a non-loopback database or when `NODE_ENV=production` unless `--confirm-database=<name> --allow-demo-on-remote` is passed (same pattern as `bootstrap:admin`). `base` is safe everywhere.
4. **Tests:** a DB test runs `base` twice (idempotent), runs `demo` then `--purge-demo` and asserts no demo rows remain, and the test DB guard (`sineva_compro_app_test` only) still applies.
5. Local setup in the README gains: `npm run db:migrate && npm run db:seed -- --demo`.

`page_content.data` uses JSONB on purpose: page sections are fixed in code and change with design iterations, so a per-page schema in code (validated on write and read) is cheaper to evolve than a table per section. Collections that are listed, filtered, or linked (services, work, posts, FAQ) get real tables.

## 7. Testing (TDD, per ticket)

- Unit: validators (lengths, slug, em dash rule, WhatsApp E.164, page schemas), encryption round-trip, redirect resolution.
- Database: constraints (unique slug per locale, unique waitlist email), transactions (publish snapshot, slug change + redirect atomic), capability guards per role.
- Integration (HTTP): admin pages require auth and role, public pages render published data only, revalidation after save, media upload against a SeaweedFS container in Compose (PutObject, GetObject, DeleteObject, HeadObject, presigned GET).
- E2E (CPR-56): edit Home hero → see it live after save; publish post → appears in blog and sitemap; Editor cannot open settings/email/leads.

## 9. Risks

| Risk | Mitigation |
|---|---|
| JSONB page content drifts from code schema | Versioned per-page schema with a migration function on read; tests load every fixture through the current schema |
| Secrets in DB | Encrypted, write-only, env override, audit log, Admin-only |
| SeaweedFS S3 compatibility gaps | Integration tests on the exact operations; `MediaStore` interface allows swapping to another S3 provider |
| Editors break layout with long text | Validators share layout limits from the design docs; live counters |
| Scope growth into a page builder | Sections fixed in code (PRD non-goal); only toggles for optional sections |
